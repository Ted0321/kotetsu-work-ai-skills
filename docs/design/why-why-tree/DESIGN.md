## 0. 一言でいうと

なぜなぜ分析を「**展開 → 兄弟監査 → 停止判定**」の階層ループとしてAIに実行させ、
その過程を**ロジックツリーの成長アニメーション（HTML）**として出力するスキル。

品質の本体は3つの機構。

1. **兄弟監査** — 同じ親を持つ子ノード群を、粒度・重複・十分性で毎階層チェックする
2. **明示的停止ゲート** — 展開の前に毎ノード「掘る／止める」を判定し、判定結果を型付きリーフとして木に残す
3. **勘所のチェックリスト化** — コンサルの暗黙知を「どのフェーズの・どのルールか」まで分解して実装する

## 1. 問題設定 — 素のAIなぜなぜ分析はどう破綻するか

「なぜを5回繰り返して」とだけ指示したときの典型的な破綻。3つの設計要件はこれらの裏返しになっている。

| # | 破綻パターン | 例 | 対応する設計要件 |
|---|---|---|---|
| 1 | **言い換え** | 売上が低い ← 売上高が減少しているから | 要件1(b) |
| 2 | **飛躍** | 納期遅延 ← 経営層のコミットが弱いから（中間の因果3段を飛ぶ） | 要件1(b) |
| 3 | **粒度の不揃い** | 兄弟に「組織文化」と「先週のメール誤送信」が並ぶ | 要件1(a) |
| 4 | **人格への帰属** | ミスが多い ← 担当者の注意力不足（対策が精神論になる） | 要件3 |
| 5 | **浅すぎ／掘りすぎ** | 機械的に5回で止まる。逆に対策可能な地点を通過して哲学になる | 要件2 |
| 6 | **検証不能な原因** | 「顧客との信頼関係が弱いから」— 確かめようがない | 要件2(b)・要件3 |
| 7 | **単鎖化** | 木ではなく1本の鎖になり、複数要因の問題で主因を外す | 要件1(a) |

**X公開時の論点（仮）**: 「AIに『なぜを5回』と頼むと、3回目から言い換えが始まる」。
動画は"賢い出力"ではなく"検証しながら育つ過程"を見せる（§7）。

## 2. 全体アーキテクチャ — 一括生成ではなく「成長ループ」

### 生成方式の比較

| 方式 | 内容 | 長所 | 短所 | 評価 |
|---|---|---|---|---|
| A. 一括生成 | 1プロンプトで木を丸ごと出す | 速い・安い | 兄弟監査が構造的に不可能。ルールを列挙しても守られたか検証できない。破綻1〜7が全部残る | ✗ |
| B. DFS（1本ずつ根まで） | 古典的な「なぜ5回」の順 | 物語として自然 | 枝をまたいだ粒度が揃わない。木が偏って育ち、動画も不格好 | △ |
| **C. BFS（1階層ずつ）** | 全ノードを1階層ずつ展開し、階層ごとに監査 | **兄弟が同時に生成されるので粒度・MECEを監査できる**。動画の「層が波のように増える」絵と同型。途中停止・再開が自然 | 手数が増える（トークン増） | **◎ 推奨** |
| A案の廃棄理由の補足 | — | — | 一括生成に「自己チェックもせよ」と足しても、生成と検証が同一パス内で混ざり、検証が形骸化する（チェック済みという申告だけが残る） | — |

**推奨: C（BFS階層ループ）＋ 各階層で「生成→監査」の2パス**。

### プロトコル全体像（5フェーズ）

```
Phase 0  問題定義      曖昧な訴え → 定量化された問題文に固定（あるべき/現状/ギャップ）
                       事実の注入を1回だけ促す。なければ「仮説モード」を宣言
Phase 1..N  階層ループ  各「続行」ノードについて:
                       ① 停止ゲート（掘る/止めるを判定。止めたら型付きリーフ化）
                       ② 展開（切り口を宣言してから子2〜4個を生成。マイクロルール適用）
                       ③ 兄弟監査（粒度・重複・十分性。不合格は書き直し）
                       階層の終わりに: 現在の木を再掲（作業メモリ）＋ 寄与度メモ
Phase F  最終監査      全リーフ→根の逆読み・禁じ手スキャン・十分性の再確認
Phase G  収束          本命パス選定（寄与度×制御可能性×実行容易性）→ 打ち手・検証タスクへ接続
Phase H  出力          ツリーHTML（エージェント型）／テキスト木＋Mermaid（コピペ型）
```

**作業メモリの規約**: 毎階層の終わりに現在の木全体をインデントテキスト（エージェント型ではJSON）で再掲する。
言い換え・重複の検出は「新ノード vs 木全体」の突合であり、この再掲がその土台になる。
副産物として、チャットログ自体が「木が育つログ」になり、そのまま画面収録の素材になる。

## 3. 要件1: 階層ごとのルール設計

### 3.1 展開マイクロルール（1ノード → 子2〜4個を作るときの規約）

| # | ルール | 判定方法（AIに実行させる形） |
|---|---|---|
| R1 | **切り口宣言** | 子を書く前に「この親を何の軸で分解するか」を1行宣言する（例: 発生メカニズム／プロセス段階／主体別）。切り口なしの列挙を禁止 |
| R2 | **「だから」逆読み** | 各子について「（子）。だから（親）」と読み上げ、自然かつ十分に聞こえるかを確認。不自然なら因果でない |
| R3 | **1歩＝1因果** | 子と親の間に「中間のなぜ」を1個挿入できるか自問。挿入できるなら飛躍→分割する |
| R4 | **言い換え禁止** | 子が親（および木の既存ノード）の同義言い換えでないこと。新しい事実・機構を1つ含むこと |
| R5 | **主語と時制の明示** | 「誰が／何が・いつ」を含む文にする。「〜が徹底されていない」等の主語なし文を禁止 |
| R6 | **仕組みで語る** | 個人の注意力・意識・やる気を原因にしない。人に見えたら「なぜその人がそう行動できてしまう仕組みか」に言い換える |
| R7 | **兄弟数2〜4** | 1個なら単鎖として許容（理由明記）。5個以上は切り口の混在か粒度過細のサイン→切り口を立て直す |

### 3.2 兄弟監査（同一親の子グループ単位で毎回実行）

| 観点 | チェック内容 |
|---|---|
| **粒度** | 兄弟同士で ①抽象度 ②時間スケール ③主語の範囲 の3つが揃っているか（「組織文化」と「先週の誤送信」を並べない） |
| **重複** | どの2つの兄弟も、同一事象の言い換え・包含関係になっていないか |
| **十分性（漏れ）** | 「子の原因をすべて解消したと仮定して、親の事象は概ね消えるか」。消えないなら枝を追加するか、**「その他（未特定）」ノードを明示**して残余を隠さない |

MECEについての設計判断: 完全MECEを毎階層で強制すると木が爆発する。ここでは
「重複ゼロは厳格に・網羅は十分性テスト＋『その他』明示で担保」という**MECE"感"の運用**にする（勘所6の絞り込みと整合）。

### 3.3 監査の実装形式の比較

| 方式 | 内容 | 評価 |
|---|---|---|
| プロンプト内ルール列挙のみ | 「以上を守って生成せよ」 | ✗ 守られたか出力から判別できない |
| **生成→自己監査の2パス** | 生成後、監査結果を表形式で出力させ、不合格は書き直し | **◎ 推奨（共通コア）**。監査結果が出力に残る＝ユーザーが検証できる＋動画の演出素材になる |
| 監査を別エージェントに分離 | レビュー専用サブエージェント | ○ エージェント型のオプション（§6）。コピペ型では不可能なので共通コアにはしない |

## 4. 要件2: 深さの限界値（停止条件）

### 4.1 設計判断: 暗黙指示ではなく「明示的停止ゲート」

| 方式 | 評価 |
|---|---|
| 暗黙指示（「対策可能になったら止めて」） | ✗ 判定がAIの頭の中で消え、なぜ止めたか／なぜ掘ったかが検証できない |
| **明示ゲート（展開前に毎ノード3問に答え、判定を木に記録）** | **◎ 推奨**。判定理由が出力に残る。リーフが型付きになり、動画ではバッジとして見える。「5回」を目安から解放できる |

### 4.2 停止ゲート（展開前に毎ノードで実行する3問）

```
Q1 対策可能性: この原因に対し「誰が・何を・どう変えるか」を1文で書けるか？
   → 書ける = ● 根本原因（対策可）として停止。対策1文をノードに添付
Q2 検証可能性: データや現場観察で真偽を確かめられる粒度か？
   かつ、これ以上掘るには事実が足りないか？
   → Yes = ◐ 要検証 として停止。検証方法（何を・どこで確かめるか）を必ず添付
Q3 制御可能性: 自組織の裁量で変えられる領域か？
   → No（市況・天災・法規制など） = ○ 所与 として停止。前提条件として記録し、掘らない
すべてNo → 続行（次の階層で展開）
```

### 4.3 型付きリーフの一覧

| マーク | 型 | 停止理由 | ノードに残すもの |
|---|---|---|---|
| ● | 根本原因（対策可） | 具体的な打ち手を1文で書ける | 打ち手1文 |
| ◐ | 要検証 | 検証可能な粒度に達した／事実がないと先へ進めない | 検証方法（データ・現場・ヒアリング先） |
| ○ | 所与 | 制御可能範囲の外 | 前提として明記（打ち手の制約条件になる） |
| △ | 要調査 | 情報不足で仮説の域を出ない | ユーザーへの質問リスト |

`◐`（要検証）の設計意図: AIはユーザーの現場の事実を知らない。**知らないことを「もっともらしい断定」で埋めず、
検証タスクとして木に残す**のがコンサル品質の生命線（deep-research-report の「盛らない原則」の類縁）。

### 4.4 安全弁

- **深さ5で強制レビュー**（この枝を掘り続ける価値を寄与度で説明できなければ打ち切り）、**深さ7でハード停止**
- **循環検出**: 新ノードが祖先の言い換えなら循環と判定して停止（例: 売上減→投資減→品質低下→売上減）
- **ノード総数の目安25・上限30**: 超えそうなら寄与度の低い枝を「畳む」（勘所6。木の可読性＝動画の可読性でもある）
- 「なぜ5回」は**目安であって停止条件ではない**、とSKILL.mdに明記する（3回で●に達したら止まってよい）

## 5. 要件3: コンサルタント視点の組み込み

### 5.1 実装形式の比較

| 方式 | 内容 | 評価 |
|---|---|---|
| ペルソナ付与 | 「一流コンサルとして振る舞え」 | ✗ 単体では挙動が変わらない。何が"プロの動き"かが未定義のまま |
| **フェーズ別チェックリスト化** | 勘所を「どのフェーズの・どの判定か」に分解して埋め込む | **◎ 推奨（本体）**。§3・§4のルール群はこの分解の結果 |
| 良例・悪例のfew-shot | 悪→良の書き換えペアを見せる | **○ 併用（最小3組）**。「粒度」「飛躍」のような感覚語はルールより例が伝わる |

### 5.2 勘所 → 実装マッピング（このスキルの頭脳）

| # | コンサルの勘所 | 実装先 |
|---|---|---|
| 1 | 問題を定量で固定する（あるべき/現状/ギャップ。曖昧な問題文から良い木は生えない） | Phase 0 |
| 2 | 事実と仮説を分ける。仮説を断定調で書かない | ノード属性 `kind: 事実/仮説`＋仮説モード宣言＋◐ |
| 3 | 人を責めず仕組みを責める | R6 |
| 4 | 飛躍しない（Why so? / So what? が双方向に通る） | R2・R3 |
| 5 | 兄弟の粒度を揃える | 兄弟監査・粒度3観点 |
| 6 | 全部を掘らない。効くところに絞る（パレート） | 階層ごとの寄与度メモ→本命パス選定・ノード総数上限 |
| 7 | 制御可能性で切る（変えられないことを議論しない） | 停止ゲートQ3 |
| 8 | 対策から逆算して止める（対策が書けたら根本原因） | 停止ゲートQ1 |
| 9 | 三現主義（現場・現物・現実。データで確かめる） | ◐に検証方法必須・Phase 0の事実注入 |
| 10 | 出す前に自分で潰す（セルフレビュー） | Phase F 最終監査 |

### 5.3 few-shot（悪→良の3組。SKILL.mdに収録）

| 破綻 | 悪例 | 良例 |
|---|---|---|
| 言い換え | 売上が下がった ← 売上高が減少しているから | ← 主力製品Aの新規受注件数が前年比4割減ったから |
| 飛躍 | 納期遅延 ← 経営層のコミットが弱いから | ← 見積り根拠をレビューする関門がないから（1歩だけ掘る） |
| 人格帰属 | 入力ミスが多い ← 担当者の注意力不足 | ← 目視転記に依存し、照合工程が存在しないから |

### 5.4 事実の注入と仮説モード

Phase 0 の終わりに1回だけ「わかっている事実・データがあれば貼ってください。なければ仮説モードで進めます」と促す。
- 事実あり → 該当ノードを `事実` として扱い、寄与度も実数で置ける
- 事実なし → **仮説モードを宣言**し、全ノードを仮説として生成。◐リーフが自然に増え、
  「検証計画つきの仮説の木」という誠実な成果物になる（AIが知ったかぶりで現場を断定する事故を構造的に防ぐ）

## 6. 自己検証（Phase F 最終監査）

共通コア（コピペ型でも実行可能な自己監査）:

1. **全パス逆読み**: すべてのリーフから根まで「だから」で読み上げ、通らないリンクを修正
2. **禁じ手スキャン**: 言い換え・人格帰属・主語なし文・検証方法のない◐ を全ノード走査
3. **十分性の再確認**: 各分岐で「子を全部解消したら親は消えるか」を再質問
4. **本命パス選定**: 寄与度×制御可能性×実行容易性で「最も効く1本道」を選び、理由を1文で言う

エージェント型のみのオプション（v0.2以降でも可）:
- **レビュー・サブエージェント**（悪魔の代弁者）: 木を渡し「最も怪しいリンク3つを反証せよ」とだけ指示する別エージェント。
  生成した本人がレビューする限界を超える。過去バズ「サブエージェント可視化」と物語がつながる（動画でレビューアが動く絵が撮れる）

## 7. アウトプット形式 — 「育つ様子」の見せ方

### 7.1 比較

| 案 | 内容 | 動画映え | 配布価値 | 実装コスト | 破綻リスク |
|---|---|---|---|---|---|
| A. Mermaid段階レンダリング | 階層ごとにMermaidを出し、プレビューを順に撮る | △ 段階間で自動レイアウトが再計算され、**ノードが跳ぶ**。ジャンプカットの連続になる | ○ どのMd環境でも貼れる | 低 | 低 |
| **B. HTML成長アニメーション（テンプレート方式）** | スキルが**ツリーJSONだけ**を生成し、`assets/tree-template.html` に流し込む。テンプレが最終形のレイアウトを先に計算し、ノードを**その場に**順次出現させる | ◎ 位置が動かないので成長が有機的。検証・停止判定を演出として見せられる。16:9固定・録画モードつき | ◎ ハウスデザイン（白×濃紺）なので**そのまま配れる資料**になる。A4印刷可 | 中（テンプレは1回作れば全案件で再利用） | 低（AIは座標・SVGを書かない。JSONが正しければ壊れない） |
| C. ターミナル描画 | CLI上でテキスト木が伸びる | ○ 開発者感はあるが、過去のサブエージェント可視化動画と絵が被る。コンサル成果物感がない | ✗ | 中 | 中 |
| D. 静的スライド（pptx/画像） | 完成形を1枚絵で | △ 成長が見えない＝今回の企画意図と不一致 | ○ | 低 | 低 |

**推奨: B を主役、A を過程ログとして併用**（分析中の各階層スナップショットはテキスト木＋Mermaidで逐次出力。
これ自体が「チャット内でも木が育って見える」進行表示になり、コピペ型の主出力にもなる）。

### 7.2 B案の設計詳細

- **デザインはハウス標準を継承**: `html-report-design` と同じトークン（紙白・インク黒・グレー2段・濃紺 #173f66・細罫。
  カード/影/角丸/グラデ禁止）。「AIデモの画面」ではなく「コンサルの配布物が動いている」絵にする。既存2スキルとの世界観の一貫性がブランドになる
- **16:9ステージ（1280×720論理座標）**: X動画にそのままクロップできる。録画モード（UIを隠しステージだけにする）つき
- **成長タイムライン**: 問題定義 → 階層ごとの波状出現 → 検証ログ（✓粒度・✓網羅・✓逆読み）→ 停止バッジ（●◐○）→
  寄与度表示 → 本命パス点灯（他を減光）→ 打ち手チップ。再生/一時停止/ステップ送り/速度/リプレイ
- **検証の可視化が差別化の本体**: 「木が出てくる」だけなら既視感がある。**階層ごとにチェックが走って✓が付く過程**が
  「ちゃんと考えている」ことの絵になる（=要件1〜3がそのまま演出になる）
- `?end=1` で最終フレーム直行（サムネイル・静止画切り出し用）。`prefers-reduced-motion` では最終形を静的表示
- **実装方式は deep-research-report と同じ「assets テンプレート」路線**: AIの仕事はJSON生成まで。
  レイアウト計算（列位置・行割り・エッジ経路）はテンプレのJSが行う。ここをAI任せにしないことが再現性の生命線

### 7.3 データモデル（スキルとテンプレの契約）

```json
{
  "problem": {
    "raw": "プロジェクトがいつも遅れる",
    "defined": "直近4PJ中3PJで納期が1ヶ月以上遅延した",
    "gap": { "tobe": "全PJで合意納期を遵守", "asis": "直近4PJ中3PJが1ヶ月以上遅延" }
  },
  "mode": "hypothesis",
  "nodes": [
    {
      "id": "B1a", "parent": "B1", "level": 3,
      "text": "「要件定義完了」の判定基準が社内標準として定義されていない",
```

## 8. 配布形態 — コピペ型／エージェント型

| 案 | 評価 |
|---|---|
| コピペ型のみ | リーチは最大だが、SKILL.mdにHTMLテンプレを埋め込むと肥大化（テンプレ約300行）。動画の主役であるHTML出力が不安定になる |
| エージェント型のみ | 完成体験は最高だが、ChatGPT/Geminiユーザーを全部捨てる（このリポジトリの流儀にも反する） |
| **両対応（共通コア＋出力分岐）** | **◎ 推奨** |

**推奨構成**:

- **共通コア（SKILL.md本体）** = 分析プロトコル（§2〜§6）。環境非依存。コピペでもスキル導入でも同じ品質で分析が走る
- **出力の分岐**:
  - コピペ型（Claude/ChatGPT/Gemini）: 階層ごとのテキスト木スナップショット＋最終Mermaid図（型付きマーク・本命パス太字）
  - エージェント型（Claude Code/Codex）: 上記に加えて `assets/tree-template.html` へJSONを流し込み、成長アニメHTMLを出力
- **導線設計**: コピペ型の出力末尾に「動くツリーHTMLはエージェント型で: `npx skills add Ted0321/kotetsu-work-ai-skills@why-why-tree`」
  を1行添える。X動画（HTML版）→ コピペで試す → 導入、という既存ロードマップと同じ導線が引ける

ディレクトリ構成（実装時）:

```
skills/why-why-tree/
├── SKILL.md                       # 共通コア＋出力分岐
├── assets/tree-template.html      # 成長アニメ・テンプレ（JSON差し込み）
├── examples/sample_input_output.md
├── examples/sample_run/tree.json  # サンプル問題の完全な出力データ
├── agents/openai.yaml             # Codex向けメタデータ（既存スキルと同様）
└── README.md
```
