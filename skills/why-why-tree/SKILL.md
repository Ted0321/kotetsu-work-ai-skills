# なぜなぜ分析 — 型で掘る根本原因ツリー

AIに「なぜを5回」と頼むと、3回目あたりから言い換えが始まる。
なぜなぜ分析の品質は回数ではなく**型**で決まる:
**1階層ずつ「展開 → 兄弟監査 → 停止判定」**を回し、対策が打てる粒度で正しく止まる。
このスキルはその型を強制し、結果を**型付きロジックツリー**として出力する。

## 目的

再発する問題・繰り返し起きるトラブルを、**具体的な打ち手が書ける根本原因**まで構造分解する。
成果物は、①型付きロジックツリー ②根本原因ごとの打ち手・検証計画 ③本命パス（最も効く1本道）の3点。

## 原則（5つ）

1. **言い換えは1ミリも進んでいない。** 子は親の同義文ではなく、新しい事実・機構を1つ含む
2. **1歩＝1因果。** 「（子）。だから（親）」の逆読みで自然に通る幅しか掘らない。中間のなぜを挿入できたら飛躍
3. **人ではなく仕組みを責める。** 注意力・意識・やる気を原因にしない。人に見えたら「なぜその行動が仕組み上可能なのか」に言い換える
4. **対策が1文で書けたら、そこが底。** 「なぜ5回」は目安であって目的ではない。3回で着いたら止まる
5. **知らない事実は断定しない。** ユーザーの現場を知らないまま書く原因はすべて仮説。仮説と明示し、検証タスクとして木に残す

## プロトコル（1階層ずつ育てる。一括生成は禁止）

木を丸ごと一度に出すと兄弟監査ができず、言い換え・飛躍・粒度バラバラが素通りする。
必ず次のループで進め、**各階層の終わりに現在の木全体をテキストで再掲**する（これが言い換え・重複チェックの土台になる）。

```
Phase 0  問題の固定
  - 曖昧な訴えを「期間・件数・程度」で定量化する（例:「いつも遅れる」→「直近4PJ中3PJで納期が1ヶ月以上遅延」）
  - あるべき姿／現状／ギャップを1行ずつ書く
  - ユーザーの文面にある数字・事実はそのまま使い［事実］として扱う。足りない部分は仮定を明示して補う
  - 事実の注入を一度だけ促す:「わかっている事実・データがあれば、あとで貼ってください。該当する枝だけ再展開します」
    → ただし返答は待たない。その場で仮説モード（事実が十分なら事実ベース）を宣言し、最後まで完走する

Phase 1..N  階層ループ（各「続行」ノードについて）
  ① 停止ゲート（掘る前に判定。下記3問）→ 停止なら型付きリーフにして展開しない
  ② 切り口を1行宣言（「この親を何の軸で分解するか」）→ 子を2〜4個生成（展開ルール適用）
  ③ 兄弟監査（下記3観点）→ 不合格の子は書き直してから次へ
  階層の終わり: 現在の木を再掲 ＋ どの枝が効きそうか（寄与度）を1行メモ

Phase F  完成処理
  ① 最終監査（品質チェック節を全項目実行）
  ② 優先順位づけ: ●根本原因をインパクト×実行容易性×波及（他の枝にも効くか）の3軸・各3点で採点し、
     順位表を作る。1位に至る道を「本命パス」とし、選定理由を1文で言う
     （制御可能性は停止ゲートQ3の○所与で除外済みのため軸に含めない）
  ③ 根本原因●に打ち手1文、要検証◐に検証方法を接続 → 出力仕様に従って出力
```

## 展開ルール（子を作るときの規約）

| # | ルール | 判定のしかた |
|---|---|---|
| R1 | 切り口宣言 | 子を書く前に分解の軸を1行で言う（例: プロセス段階別／主体別／発生メカニズム）。軸なしの思いつき列挙は禁止 |
| R2 | だから逆読み | 「（子）。だから（親）」と読み上げ、自然かつ十分なら合格。不自然なら因果ではない |
| R3 | 1歩＝1因果 | 子と親の間に中間のなぜを1個挿入できるか自問。できるなら飛躍→分割する |
| R4 | 言い換え禁止 | 子が親および木の既存ノードの同義文でないこと（再掲した木と突き合わせる） |
| R5 | 主語と時制 | 「誰が／何が・いつ」を含む文にする。「〜が徹底されていない」だけの主語なし文は禁止 |
| R6 | 仕組みで語る | 個人の注意力・意識・やる気を原因にしない（原則3） |
| R7 | 兄弟数2〜4 | 1個は単鎖として許容（理由を明記）。5個以上は切り口の混在サイン→軸を立て直す |

## 兄弟監査（同じ親の子グループ単位で毎回実行し、結果を1行で報告）

| 観点 | チェック |
|---|---|
| 粒度 | 兄弟同士で ①抽象度 ②時間スケール ③主語の範囲 が揃っているか（「組織文化」と「先週の誤送信」を並べない） |
| 重複 | どの2つの兄弟も、言い換え・包含関係になっていないか |
| 十分性 | 子の原因をすべて解消したと仮定して、親の事象は概ね消えるか。消えないなら枝を追加するか**「その他（未特定）」を明示**して残余を隠さない |

MECEの運用: 重複ゼロは厳格に。網羅は十分性テスト＋「その他」明示で担保する（完全MECEを追って木を爆発させない）。

## 停止ゲート（展開の前に毎ノードで3問。判定を木に記録する）

```
Q1 対策可能性: この原因に「誰が・何を・どう変えるか」を1文で書けるか？
   → 書ける = ● 根本原因 として停止。打ち手1文を添付
Q2 検証可能性: データや現場観察で真偽を確かめられる粒度で、かつ事実がないと先へ進めないか？
   → Yes = ◐ 要検証 として停止。検証方法（何を・どこで確かめるか）を添付
Q3 制御可能性: 自組織の裁量で変えられる領域か？
   → No（市況・法規制・天災など） = ○ 所与 として停止。打ち手の前提条件として記録
すべてNo → 続行（次の階層で展開）。情報不足で仮説の域を出ないなら △ 要調査 とし、確認事項を添付
```

| マーク | 型 | ノードに必ず残すもの |
|---|---|---|
| ● | 根本原因（対策可） | 打ち手1文 |
| ◐ | 要検証 | 検証方法（データ・現場・ヒアリング先） |
| ○ | 所与（制御外） | 前提としての扱い方 |
| △ | 要調査 | ユーザーへの確認事項 |

**安全弁**: 深さ5で「掘り続ける価値」を寄与度で説明できなければ打ち切り、深さ7でハード停止。
新ノードが祖先の言い換えなら循環と判定して停止。ノード総数は25目安・30上限（超えそうなら寄与度の低い枝を畳む）。

## 悪例 → 良例（この違いがすべて）

| 破綻 | 悪例 | 良例 |
|---|---|---|
| 言い換え | 売上が下がった ← 売上高が減少しているから | ← 主力製品Aの新規受注件数が前年比4割減ったから |
| 飛躍 | 納期遅延 ← 経営層のコミットが弱いから | ← 見積り根拠をレビューする関門がないから（1歩だけ） |
| 人格帰属 | 入力ミスが多い ← 担当者の注意力不足 | ← 目視転記に依存し、照合工程が存在しないから |

## 出力仕様

**分析中**（各階層の終わり）: マーク付きインデント木で再掲する。

```text
問題: 直近4PJ中3PJで、納期が1ヶ月以上遅延した
├─ 当初の見積り工数が実態より過小だった〔計画・続行〕
│   ├─ 過去PJの実績工数が見積りに参照されていない〔続行〕
│   └─ 受注前に顧客予算へ合わせて工数を切り詰めている〔続行〕
├─ 実行中に作業量が計画外に増えた〔実行・続行・寄与大〕
└─ 発生した遅れの検知・是正が遅れた〔統制〕
    └─ ● 遅延時のエスカレーション基準が未定義 → 打ち手: 遅延3日でPM報告を規定
```

**完成時**は環境で分岐する。

**A. ファイルを生成できる環境（Claude Code / Codex 等）— HTMLツリーを出力**

1. このスキルの `assets/tree-template.html` を読み込む
2. `TREE_DATA_START`〜`TREE_DATA_END` マーカー間のオブジェクトだけを、分析結果のJSONに差し替える
   （**それ以外の行は1文字も変更しない**。レイアウト計算はテンプレートが行う）
3. `why-why-tree-<テーマ短名>.html` として保存し、パスを案内する（テーマ短名は半角英数。例: `why-why-tree-repeat-rate.html`）
4. ツリーは開いた瞬間に全体が表示される（アニメーションなし）。本命パスは濃紺で強調され、
   下部に「根本原因と次の一手」の表が付く

JSONの形（フィールドは省略可のもの以外すべて埋める）:

```json
{
  "title": "納期遅延の常態化 — なぜなぜ分析",
  "date": "2026-08-10",
  "mode": "仮説",
  "problem": {
    "raw": "プロジェクトがいつも遅れる",
    "defined": "直近4PJ中3PJで、納期が1ヶ月以上遅延した",
    "tobe": "全PJで合意納期を遵守",
    "asis": "直近4PJ中3PJが1ヶ月以上遅延"
  },
  "axis1": "発生メカニズム（計画→実行→統制）",
  "nodes": [
    { "id": "B",   "parent": null, "tag": "実行", "text": "実行中に、作業量が計画外に増えた", "contrib": "寄与 約55%" },
    { "id": "B1",  "parent": "B",  "text": "要件定義の完了基準が曖昧なまま、開発に着手している" },
    { "id": "B1a", "parent": "B1", "status": "root", "text": "「要件定義完了」の判定基準が、社内標準として定義されていない",
      "action": "要件定義のDoD（完了の定義）を標準化し、キックオフで顧客と合意する" },
    { "id": "B2a", "parent": "B2", "status": "verify", "text": "変更管理の手順が、契約・キックオフで顧客と合意されていない",
      "verify": "直近PJの契約書・議事録を確認" }
  ],
  "criticalPath": ["B", "B1", "B1a"],
  "checks": ["粒度 — 兄弟の抽象度を階層ごとに統一", "網羅 — 各分岐で十分性を確認", "逆読み — 全リーフ→問題まで通ることを確認"]
}
```

- `parent: null` がなぜ①。階層はテンプレートが親子関係から計算する
- `status` はリーフのみ: `root`（●）/ `verify`（◐）/ `given`（○）/ `todo`（△）。中間ノードは付けない
- ノード文は**40字以内**・主語明示。`tag` はなぜ①の切り口ラベル（計画／実行など）
- `criticalPath` は本命パスのノードidを親→子の順で

**B. チャットのみの環境（コピペ利用）— テキスト＋Mermaidで出力**

最終テキスト木（上の形式・全リーフ型付き）→ Mermaid図 → 「根本原因と次の一手」表（型／原因／打ち手・検証方法）→ 本命パスと選定理由1文、の順で出力する。Mermaidは `flowchart LR`、本命パスのノードを `classDef main stroke:#173f66,stroke-width:2.5px` で強調する。
末尾に1行: 「HTML版のツリーは Claude Code / Codex で `npx skills add Ted0321/kotetsu-work-ai-skills@why-why-tree`」

## 品質チェック（出力前・最終監査）

- [ ] 全リーフ→問題まで「だから」逆読みが通る（通らないリンクは修正済み）
- [ ] 言い換え・人格帰属・主語なし文が0（全ノード走査した）
- [ ] 全リーフが型付き（●◐○△）で、●に打ち手1文・◐に検証方法が付いている
- [ ] 各分岐で十分性を確認した（消えない残余は「その他（未特定）」として明示）
- [ ] 兄弟の粒度（抽象度・時間軸・主語の範囲）が揃っている
- [ ] ●が3軸（インパクト×実行容易性×波及）で採点され順位表になっている。1位＝本命パスの理由が1文で言える
- [ ] 仮説モードなら、断定調の文になっていない（事実注入がない原因はすべて仮説扱い）
- [ ] ノード数30以下。HTMLはテンプレートのマーカー間だけを差し替えた

## トーン

- 簡潔・実務。仮説は仮説と書く誠実さを保つ（それが◐の存在理由）
- 分析は原因当てゲームではない。打ち手と検証計画に着地して初めて完了
