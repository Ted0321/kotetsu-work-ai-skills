# 入出力サンプル

## サンプル入力

```text
うちの開発プロジェクト、いつも納期が遅れるんだよね。なぜなぜ分析やってみて。
```

## サンプル出力（理想イメージ・抜粋）

```markdown
## Phase 0 — 問題の固定

「いつも遅れる」を定量化します。
- あるべき: 全PJで合意納期を遵守
- 現状: 直近4PJ中3PJで納期が1ヶ月以上遅延（と仮置き）
- 問題文: **直近4PJ中3PJで、納期が1ヶ月以上遅延した**

わかっている事実・データがあれば貼ってください（遅延の内訳、PJ数、議事録など）。
なければこのまま**仮説モード**で進めます — 全ノードを仮説として扱い、検証を前提とした木を作ります。

## なぜ① — 切り口: 遅延の発生メカニズム（計画→実行→統制）

├─ 当初の見積り工数が、実態より過小だった〔計画・続行〕
├─ 実行中に、作業量が計画外に増えた〔実行・続行〕
└─ 発生した遅れの検知・是正が遅れた〔統制・続行〕

兄弟監査: 粒度=3枝とも工程レベルで統一 ✓ ／ 重複なし ✓ ／
十分性=計画で小さく・実行で増え・統制で気づけない、で発生源を網羅 ✓

## なぜ② — 各枝を1歩ずつ

（停止ゲートの例）
「遅延発生時のエスカレーション基準が決まっていない」
→ Q1: 打ち手を1文で書ける（「遅延3日でPM報告・1週間で上程」を規定）→ **● 根本原因として停止**

…（なぜ③まで同様に展開。各階層の終わりに木全体を再掲）…

## 最終ツリー（3階層で停止条件に到達）

問題: 直近4PJ中3PJで、納期が1ヶ月以上遅延した
├─ 当初の見積り工数が実態より過小だった〔計画・寄与約30%〕
│   ├─ 過去PJの実績工数が見積りに参照されていない
│   │   └─ ● 完了時に実績工数を記録・分析する工程が標準プロセスにない
│   └─ 受注前に顧客予算へ合わせて工数を切り詰めている
│       └─ ● 見積りの最終承認が営業部門で完結し、PMレビューを通らない
├─ 実行中に作業量が計画外に増えた〔実行・寄与約55%〕★本命
│   ├─ 要件定義の完了基準が曖昧なまま開発に着手している ★
│   │   └─ ● 「要件定義完了」の判定基準が社内標準として定義されていない ★
│   └─ 追加要望を変更管理の手続きなしで受け入れている
│       └─ ◐ 変更管理の手順が契約・キックオフで顧客と合意されていない
│           （検証: 直近PJの契約書・議事録）
└─ 発生した遅れの検知・是正が遅れた〔統制・寄与約15%〕
    ├─ 進捗が自己申告のみで成果物で確認されていない
    │   └─ ● タスクごとの完了基準（成果物）がWBSに定義されていない
    └─ ● 遅延発生時のエスカレーション基準が決まっていない

## 根本原因と次の一手

| 型 | 原因 | 次の一手 |
|---|---|---|
| ● 対策可 | 実績工数の記録・分析工程が標準にない | 完了報告に実績記録と差異分析を必須化 |
| ● 対策可 | 「要件定義完了」の判定基準が社内標準にない **（本命）** | 要件定義のDoDを標準化し、キックオフで顧客と合意 |
| ◐ 要検証 | 変更管理手順が顧客と合意されていない | 検証: 直近PJの契約書・議事録を確認 |
| …他 | | |

**本命パス**: 実行起因 → 完了基準が曖昧なまま着手 → 社内標準の不在。
寄与度が最大の実行起因のうち最上流（着手判定）にあり、自社の標準整備だけで着手できるため。

（Claude Code / Codex の場合はここで）

型付きツリー全体・本命パス・対策表が1画面で表示されます（A4印刷可）。
```
